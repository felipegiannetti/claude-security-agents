# Compliance Framework Mapping (NIST CSF 2.0 / ISO 27001)

## What this is

`knowledge/compliance/nist-mapping.json` and `knowledge/compliance/iso27001-mapping.json` map a `finding.schema.json` `category` string to the relevant NIST Cybersecurity Framework 2.0 function/category and ISO/IEC 27001:2022 Annex A control(s). Looked up deterministically by `scripts/reporting/map_compliance.py`, same pattern as the MITRE ATT&CK mapping (`knowledge/mitre/attack-overview.md`) and CISA KEV correlation (`scripts/scanners/check_kev.py`) -- never generated by an LLM recalling a control ID from memory.

## Why NIST CSF 2.0, and why function-level

NIST publishes several frameworks at very different granularity -- CSF 2.0 (six functions, ~20 categories) versus SP 800-53 (hundreds of detailed controls). This project maps to **CSF 2.0 at the function/category level** (e.g. `PR.PS`, not a specific subcategory outcome statement) deliberately: the coarser level is where this project has high confidence, and a wrong subcategory-level claim is worse than a correct, if less granular, category-level one. If your engagement needs SP 800-53 control-level mapping, treat this file as a starting point, not a substitute for that separate, more detailed exercise.

## Why the ISO 27001 file only has IDs and short subjects

The ISO/IEC 27001:2022 standard text itself is copyrighted and sold by ISO -- this project has no license to reproduce its control descriptions. `iso27001-mapping.json` therefore only records the control ID (e.g. `A.8.28`) and a short, independently-written paraphrase of the control's subject (e.g. "Secure coding") -- never the standard's own wording. If you need the actual control text for an audit, you need a licensed copy of ISO/IEC 27001:2022 Annex A -- this mapping only tells you *which* control to look up, not what it says.

## Confidence caveat -- verify before a real engagement

These mappings were authored from general knowledge of the current NIST CSF 2.0 and ISO/IEC 27001:2022 structures, not validated against a live, authoritative copy of either standard at generation time. Before using this in a real compliance-facing deliverable (an audit, a client report a compliance team will rely on), have someone with current access to the actual standards spot-check the mappings for the categories your engagement actually surfaced. Treat this file the same way you would treat any other unverified reference: useful as a strong starting point, not a substitute for a check against the source.

## Scope -- core categories only, same discipline as MITRE ATT&CK

Both files currently cover the same ~15-16 core finding categories as the ATT&CK mapping, not the full ~45-category set. A category absent from either file has no confirmed mapping yet -- `map_compliance.py` omits the field rather than guessing, and that omission should never be read as "this finding has no compliance relevance."

## Relationship to severity and priority

Framework alignment (ATT&CK, NIST, ISO) is additive context for the reader -- it never substitutes for or adjusts a finding's `severity` or `priority` fields, which remain governed entirely by `config/severity.config.yaml` and `config/priority.config.yaml`. A finding mapped to a NIST/ISO control is not thereby more or less severe; the mapping only tells the reader which of their own compliance obligations the finding is relevant to.
